# ML-1 — the container, RUN

Generated by `run_container_load.py`.

## The finding, which is not a latency number

`README.md` listed this open: *`docker build` runs clean ... what has
not happened is running the service inside it under load.* Running it
found the image **could not start at all**:

```
OSError: libgomp.so.1: cannot open shared object file
```

lightgbm links against libgomp — the GNU OpenMP runtime — and
`python:3.12-slim` does not ship it. The pip install of a manylinux
wheel resolves and completes perfectly; the shared library it needs at
**load** time is a system package pip knows nothing about. So the build
was green and the service could not start, and that stayed true for as
long as nobody ran it.

**That is the entire argument for running a container rather than
building one.** `docker build` proves the layers resolve. It proves
nothing about whether the thing inside starts.

Fixed by installing `libgomp1` before the pip layer, so a requirements
change does not re-run apt.

## A second thing running it surfaced

```
/usr/local/lib/python3.12/site-packages/sklearn/base.py:525: InconsistentVersionWarning: Trying to unpickle estimator LabelEncoder from version 1.8.0 
/usr/local/lib/python3.12/site-packages/sklearn/base.py:525: InconsistentVersionWarning: Trying to unpickle estimator IsotonicRegression from version 
```

The model artifact was pickled under scikit-learn **1.8.0** and the
image resolves **1.9.0**. scikit-learn's own warning says this *"might
lead to breaking code or invalid results"*.

It is a warning rather than a failure, which is exactly what makes it
worth recording: the service starts, scores, and returns numbers that
may silently differ from the ones the model was validated against. A
shipped model artifact and the environment that unpickles it are a
versioned pair, and `requirements.txt` pins neither end of it.

## What this deliberately does NOT claim

**It is not a container-versus-host comparison**, and the README's
claim that the two p99s differ remains untested.

The load is driven from inside WSL, because the container publishes on
WSL's loopback and reaching it from Windows depends on WSL2's localhost
forwarding — which on this machine works intermittently, the same
flakiness that made Redis and Kafka unreachable earlier in this
project. A probe failing for that reason reports *container did not
become healthy* about a container that is serving perfectly.

So a host baseline would carry a Windows client over loopback where
this carries a Linux client on the same kernel. The two differ in the
CLIENT as well as the server, and putting them in one table as a
container-overhead figure would be the misleading version of this
document.

- **The host was busy.** Load average during the run: `7.72 10.04 5.28`.
  So these latencies are a **floor** — the number this service beats on
  a quiet machine — and not its best. Quoting them as the service's
  latency would be the flattering direction to be wrong in, which is
  the direction to state rather than the one to leave out.
- **No resource limits.** A production container has a CPU quota and a
  memory limit; this has neither, so it measures overhead rather than
  constraint.
- **One run.** Nothing here separates run-to-run variance from a real
  difference.
