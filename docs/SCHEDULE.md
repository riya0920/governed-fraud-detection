# ML-1 — the monitoring schedule

Generated by `run_schedule.py` over 336 hours of simulated time
containing a flapping signal, a real sustained drift, and a three-day
outage of the monitoring job itself.

`monitor.py` produced the report and `src/retraining.py` ranked the
triggers. Nothing ran either — and a monitoring plan that executes when
somebody remembers to execute it gets run *after* an incident, to
explain it, rather than before one, to catch it.

## 1. Cadence follows signal latency

| check | cadence | needs labels | detection delay from hysteresis |
|---|---|---|---|
| `alert_rate` | 60 min | no | 120 min |
| `score_psi` | 360 min | no | 720 min |
| `feature_psi` | 1 days | no | 2 days |
| `performance` | 7 days | yes | 14 days |

`monitor.py` already ranks its signals by how fast they can possibly
fire. Running all four on one cadence throws the fast ones away, and
running the label-dependent check hourly is worse than useless — it
recomputes the same stale answer sixty times a day and teaches whoever
reads it that the number never moves.

### Detection delay on the one event that mattered

| | hours |
|---|---|
| real drift began | 168 |
| page fired | 194 |
| **total delay** | **26** |
| ...of which the monitoring outage | 24 |
| ...of which hysteresis | 2 |
| ...of which cadence rounding | 0 |

Worth separating, because the three have different fixes. The
hysteresis cost is a deliberate 2 hours and buys the reduction in
the next table. The 24 hours of outage are not a tuning question at
all — they are the monitoring job being down, and no threshold
setting recovers them. **The outage was the dominant cost of
detection delay in this run**, which is the opposite of where
attention usually goes.

## 3. What hysteresis bought

| | pages |
|---|---|
| a job that pages on every breaching run | 60 |
| this schedule | **1** |

Hours 72-95 are one event that crosses the threshold every other hour —
twelve crossings. PSI over a rolling window does exactly this. Without
hysteresis that is twelve pages for one event, and three pages for one
event already trains the on-call to acknowledge without looking, which
is the state in which the next real page is also ignored.

**The cost is stated rather than skipped:** requiring 3 consecutive
breaches DELAYS detection by 2 intervals — 120 minutes on the hourly
check. That is the trade, not a free improvement.

Firing is slower than forgiving on purpose: 3 breaches to page, 2
clean runs to clear. A control that forgives as slowly as it fires
stays lit long after the incident and stops meaning anything.

## 4. A missed monitoring run is not backfilled

**This is the opposite of SE-2's settlement catch-up, and deliberately
so.** A settlement cycle must process every missed date: the state is
cumulative and skipping one leaves a hole. Monitoring is not
cumulative. If the box was down for three days, replaying seventy-two
monitor runs pages the on-call for drift that has already resolved and
buries the current state under history. What matters is the answer now.

So the missed runs coalesce into one — and the **count is reported**,
because *we have not monitored for three days* is itself a finding and
silently catching up conceals it.

Note where the outage sits in this run: hours 120-191 overlap the start
of the real drift at hour 168. **The outage hid the first day of it.**
The schedule cannot recover that day; what it can do is say so, which
is why the missed count travels with the first run back.

## 5. The cooldown the alert cannot override

A fired trigger is a reason to *consider* retraining, not a reason to
retrain now. Two fits inside 72 hours means the second trains on a
window the first already reacted to, and neither can be judged against
a clean comparison. `src/retraining.py` already declines to fire on a
*warn* for the same reason — retraining on a warn burns the clean
comparison window a page will need later.

## What this still is not

- **Nothing invokes it.** This is the scheduling LOGIC — what is due,
  what pages, what may retrain — and it still needs a cron entry, a
  systemd timer or an Airflow DAG to call it. That is deliberate: the
  decisions above are the part worth testing, and they are testable
  precisely because they take `now` as a parameter instead of reading
  the clock.
- **Nothing is actually paged.** There is no PagerDuty integration, so
  `page_now` is a return value rather than a phone ringing.
- **The drift here is scripted.** The event schedule is a function of
  the hour, not a real score distribution moving. `run_retraining.py`
  drives the trigger logic against real monitor output; this drives the
  cadence and hysteresis against a signal shaped to exercise them.
- **One signal is simulated.** Only `alert_rate` is driven through the
  fourteen days. The other three cadences are configured and exercised
  by the tests, not by this run.
