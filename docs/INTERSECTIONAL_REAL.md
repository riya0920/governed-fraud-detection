# ML-1 — intersectional fairness on REAL protected attributes

Generated by `run_intersectional_real.py` on 15,587 real HMDA 2023
Delaware applications with race AND sex both self-reported.

## Why this run exists

`README.md` listed the sharpest limitation a fairness section can
have: *both attributes in the intersectional analysis are synthetic
overlays constructed by this repo, so no fairness number here
describes a real population.*

An intersectional metric over invented attributes measures the
generator — and the generator was written by the same author as the
metric, so a "finding" is one set of assumptions agreeing with
itself. HMDA carries two real protected attributes on the same
applicants, which is the configuration this needs and is genuinely
hard to find.

**The machinery under test is ML-1's; the decision is HMDA's** — a
mortgage approval, not a fraud score. This validates the analysis on a
real population and does not turn ML-1 into a lending model.

## The verdict

> no cell below 0.80 at this operating point

**No cell falls below 0.80 at this operating point.** That is the
honest outcome and it is reported rather than searched past.
Intersectional disparity is a thing that CAN happen, not one that
always does, and a fairness tool that only ever reports findings
is one nobody should trust.

What the run establishes is that the machinery produces a real
number on a real population — which is exactly what the README
said it could not.

**But read the direction, not only the threshold.** The
worst cell (`minority=1 , female=1`) sits at **0.8443** — below
*both* marginals (0.8569, 0.9878).
So the intersection IS worse than either attribute alone,
which is precisely the effect the module was written to
find; it simply does not cross 0.80 on this population.

Reporting that as "no finding" would throw away the
direction. A threshold verdict answers *is this
actionable today*; the ratio answers *is the effect
there*, and those are different questions.

## The constraint running it on real data exposed

`intersectional_table` iterates over `(0, 1)` for each axis, so **both
attributes must be binary.** On real HMDA that forced race down to
minority / non-minority.

That reduction is the exact aggregation ML-3's
`docs/HMDA_FAIR_LENDING.md` found hides a failing group: on the same
data the aggregate AIR passes at 0.8478 while four individual race
groups fail. So a binary intersectional table can report *no cell
below 0.80* on a population where a named group is being declined at
a failing rate — which is a limitation of the tool, not of the data,
and it is the kind that only shows up when the tool meets a
population with more than two of anything.

## What this still does not license

- **The decision is a mortgage approval.** Every caveat in
  `ml3-credit-scorecard/docs/HMDA_FAIR_LENDING.md` applies unchanged:
  no credit score, every lender in the state pooled, and a disparity
  here is an upper bound on unexplained disparity.
- **Race is self-reported and sex is partly observed.** HMDA records
  whether each was reported or inferred by the loan officer, and this
  run keeps only applications where race was reported. Sex is not
  filtered the same way, which is an inconsistency worth naming rather
  than smoothing.
- **Two attributes is not intersectionality.** Real intersectional
  analysis spans more axes than a 2-D table has room for, and the
  cell-size floor is what stops it going further — every axis added
  divides the population again.
- **ML-1's own fraud model is still fitted on generated data.** This
  run validates the ANALYSIS on a real population. The model that
  analysis is usually pointed at has not changed.
