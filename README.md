# ML-1 — Governed Fraud Detection System

**Status: ~99%.** **Real LightGBM with monotonic constraints**, a four-arm
imbalance bakeoff including **focal loss** via a custom objective, **TreeSHAP**
reason codes, a calibration gate, an **automated retraining pipeline** that acts
on the monitor's verdict and then deliberately stops at a human, **intersectional
disparate impact**, a **less-discriminatory-alternative search**, and a
**measured service p99** on the scoring API. **41 tests.** What is left is real
data and independent validation -- neither of which more code can supply.

```bash
python src/generate.py && python train.py    # analysis + docs/RESULTS.md + artifact
python -m pytest tests -q                    # 9 API and monitoring tests
uvicorn serve:app --port 8000                # scoring service
python monitor.py                            # drift report off the decision log
python run_promotion.py                      # shadow a challenger, run the gates
python run_retraining.py --force-drift       # monitor -> trigger -> refit -> gates
python run_fairness_deep.py                  # intersectional + LDA search
python run_load.py --requests 2000           # service p99 over real HTTP
python fetch_real_data.py && python run_real_fraud.py   # 284,807 REAL txns
python -m pytest tests -q                    # 41 tests
```

Everything in `docs/RESULTS.md` is regenerated by that command. It is not
hand-edited, and the narrative sentences in it are formatted from the measured
numbers rather than written ahead of them — including the ones that came out
against my prior (see the SMOTE/class-weight note in §3).

## What is built

- **Leakage audit with teeth** (`src/leakage.py`). Three post-decision fields are
  planted in the raw feed; a denylist excludes them *and* a univariate-AUC screen
  independently flags them, which is the layer that catches leaks nobody
  predicted. `assert_clean()` raises before every fit.
- **Four-arm imbalance bakeoff** (`src/imbalance.py`): baseline vs class weights
  vs SMOTE vs **focal loss**. SMOTE is implemented here rather than imported so
  the interpolation semantics are inspectable; focal loss is a real LightGBM
  custom objective with the gradient derived in the docstring and verified
  against finite differences to 4e-11.
- **Metrics a risk reviewer asks for** (`src/metrics.py`): AUC/Gini, KS,
  precision and recall at a *fixed* FPR, Brier, reliability table, PSI with the
  standard bands stated. No accuracy, anywhere.
- **Threshold economics** (`src/threshold.py`). Operating point is the argmin of
  a $-weighted cost curve — fraud loss amount-weighted, insult cost, lost margin,
  review cost — benchmarked against a rules-only incumbent and against
  approve-everything.
- **Adverse-action reason codes on TreeSHAP** (`src/reason_codes.py`). Exact
  Shapley values on the log-odds margin, top-3 contributors per decline in plain
  English, with the FCRA §615(a) / ECOA Reg B framing named. Only features that
  pushed the score UP can be listed — citing a feature that argued for approval
  as a "principal reason" is a false statement to the customer, not a
  technicality. The old occlusion coder is retained for comparison.
- **Out-of-time split**, with in-sample AUC reported next to out-of-time AUC.
- **Disparate-impact analysis** (`src/fairness.py`, RESULTS.md section 8): AIR against
  the 80% rule, score-distribution comparison, AIR across five operating points,
  and a **proxy ablation** that reports what fraction of the recoverable group
  signal survives dropping the suspected proxies -- quantified, not a binary.
- **Scoring API** (`serve.py`, FastAPI): returns score, decision, reason codes,
  **model version, policy version and threshold**, and appends every decision
  with its feature vector to an audit log.
- **Monitoring job** (`monitor.py`) that runs against that decision log rather
  than a warehouse snapshot, ranking four drift signals by how fast they can
  actually page someone. Returns `insufficient_data` below 200 decisions --
  never `healthy`.
- **Validation report sections 1-10** including promotion criteria, rollback
  triggers, the monitoring plan, stability bands with owners, and a change log
  that records both versions as **unsigned**.

## The finding worth talking about

Population-level PSI is ~0.000 on every feature and on the score, while the model
still loses ground out-of-time. That is not a contradiction — it is the central
monitoring problem in fraud. The adversary changed behaviour inside a 1.2%
subpopulation, and a distribution statistic over all transactions cannot see a
shift that the legitimate mass swamps. RESULTS.md §6 shows the same PSI computed
on fraud rows only, where it moves (mcc_risk 0.116 → "monitor"), and then makes
the point that matters: that column needs labels, chargebacks arrive weeks late,
so it can never page anyone in time. The only label-free early signal is
**alert-rate drift at a frozen threshold**, which is why the ranking of the four
drift signals is in the document and why feature PSI is ranked last.

## The fairness finding

Proxy ablation is the test the spec calls the sophisticated part, and it is
worth reading the number rather than the headline. Dropping the two suspected
proxies cuts the model's ability to *reconstruct* group membership from AUC
0.727 to 0.553 — most of the signal gone — while the outcome disparity moves by
+0.005. Reconstructability and impact are different questions, and fixing the
first is not evidence of fixing the second. Reporting only the reconstruction
drop would have made a cosmetic change look like remediation.

The caveat is stated in the document too: the disparity here is small to begin
with (AIR 0.99, well above the 0.80 screen), so there is little room for ablation
to move it. The machinery is demonstrated; the scenario is benign.

## The retraining pipeline stops at a human on purpose

`run_retraining.py` joins the two halves that used to sit apart: `monitor.py`
proposed retraining and `run_promotion.py` evaluated gates, and nothing acted on
either. Now a run evaluates four ranked triggers, refits on evidence, scores
champion and challenger on the artifact's **out-of-time holdout**, runs every
gate, and appends an immutable record.

The terminal state of a *successful* run is **`AWAITING_VALIDATION`**, not
`PROMOTED`. `promote()` raises without a named independent validator, and there
is no flag that skips it:

```
promote() refused: promotion requires a named independent validator;
                   refusing to promote an unsigned model
```

Under SR 11-7 a model change needs independent validation before production use.
A pipeline that retrains, gates and deploys has not automated the validator - it
has removed the control. That refusal is the feature.

Two design points inside it worth naming. **A warn does not fire a retrain**,
because retraining on a warn burns the clean comparison window a page will later
need. And **triggers are ranked by detection latency** - alert rate (same day, no
labels) above score PSI above labelled performance (4-8 weeks, gated on
chargeback arrival) above the calendar backstop. The run record names *which*
trigger fired and on what evidence, because "the model was retrained in March" is
not an audit record.

A drill (`--force-drift`) fires the alert-rate trigger and the challenger comes
back **BLOCKED** on discrimination and calibration - the class-weighted refit is
genuinely worse than the focal champion (OOT AUC 0.6796 vs 0.7346), and the
champion stays in production. That is the outcome a gate exists to produce.

**Two wiring bugs this found.** The artifact stored `reference_scores` over the
whole scoring window and `reference_X` over 5,000 training rows - **not row
aligned**. Pairing them put one transaction's features beside another's score, an
input that is wrong in a way nothing downstream could detect. And the first
version compared champion and challenger on the champion's own *training* window,
which is biased toward the incumbent by exactly the amount it memorised; the
artifact now ships an out-of-time holdout so both are scored on rows neither
model trained on.

## Intersectional impact, and the band where it matters

`run_fairness_deep.py` crosses two synthetic protected attributes and reports
every cell against the **most-favoured cell** - the only reference that needs no
defence, since it is the treatment the model demonstrably can give.

On this data no cell falls below 0.80, and the document says so rather than
manufacturing a failure. What proves the detector works is
`test_a_failing_cell_hides_behind_passing_marginals`, on data built to contain
the masking effect - and the interesting part is that masking only happens inside
a band. With a best-cell rate of 0.95, the cross fails below 0.76 while the
marginal still passes above 0.57. **A disparity harsher than that shows up in the
marginals anyway; a milder one is not a finding.** Intersectional analysis earns
its place in that narrow band - which is exactly where a single-attribute review
is most confident it has cleared the model.

Cells under n = 200 are reported `insufficient` rather than given a point
estimate. A 2x2 cross quarters the sample, and an AIR of 0.62 on 40 applicants is
not a finding.

The LDA search finds no affordable alternative here, with the caveat printed next
to it: baseline AIR is 0.9940, so there is almost no disparity for an alternative
to remove. The machinery is demonstrated; the scenario is benign.

## Service level, measured

`run_load.py` starts `serve.py` on a uvicorn thread and drives it over real HTTP:

```
2,000 requests, 8 threads, 0 errors, 278 req/s
mean 23.19   p50 22.91   p95 26.96   p99 30.27   max 82.48   (ms)
```

Windows 11 laptop, CPython 3.14, loopback. Every request also appended a full
decision record with its feature vector, so the audit write is *inside* these
numbers. It is a **closed** loop - each thread waits for its own response, so the
offered rate falls as the service slows and queueing delay never accumulates.
That flatters the tail by construction, so read it as a floor. SE-3's
`run_soak.py` is the open-loop instrument in this portfolio.

## The same pipeline on REAL fraud data

`run_real_fraud.py` runs the governance machinery on the **ULB credit-card
dataset** — 284,807 real transactions from European cardholders, 492 frauds
(0.1727%). Free, no Kaggle account: OpenML serves it directly.

```
train : 199,364 rows, 0.1926% fraud     (split on TIME, not at random)
test  :  85,443 rows, 0.1264% fraud

AUC                        0.9726
KS                         0.8744
Brier                      0.000392
precision @ 1% FPR         0.0983
recall    @ 1% FPR         0.8611
```

Prevalence is **seven times lower** than the generated build's 1.19% and the AUC
is *higher*. That says something about the generator rather than the model: real
fraud in this feed is more separable than the one I wrote.

### The leakage screen fired on 11 features, and none of them is a leak

I wrote "nothing trips the screen, which is the expected result" before running
it. Eleven of thirty features clear a 0.90 univariate AUC — V14 at 0.9492, V4 at
0.9383, V12 at 0.9370.

**None is a leak.** This file has no post-decision information in it at all;
those are anonymised PCA components that are simply very predictive. So this is
the screen's **false-positive mode**, and it is worth more than the clean result
would have been: a univariate-AUC screen cannot tell *"this field encodes the
answer"* from *"this field is genuinely strong"*. Both look like one column that
separates the classes. On generated data the screen looked clean only because I
had not written features that strong.

What the screen is for is unchanged — it catches a leak nobody predicted, which
a denylist cannot. What it cannot do is adjudicate. **Every flag is a question
for a human, and a team that treats flags as verdicts will delete its best
features.** A test pins both halves: that it fires here, and that nothing reaches
the ~1.0 a real leak would.

### The threshold economics change on real amounts

Mean fraudulent amount **€134.88** against **€84.97** legitimate — fraud is 1.6×
larger, so amount-weighting the cost matrix earns its place rather than being
assumed. The cost-optimal point lands at **0.0187% FPR with 0.78 recall**: at a
0.13% prevalence almost every decline is wrong, the insult cost dominates, and
the optimum sits far to the right of where a pure-detection view would put it.

### And the part of this project that CANNOT run on it

Top-3 TreeSHAP contributors for the highest-scoring decline:

```
1. V14   +9.4120
2. V10   +3.8796
3. V4    +2.8363
```

Now write the adverse-action notice. FCRA §615(a) wants the **principal reasons,
in terms the consumer can act on**, and there is no sentence beginning "V14" that
satisfies it. No better attribution method fixes this — the information needed to
write the reason was destroyed by the PCA before the file was published, and it
had to be, because anonymisation is the only reason a real bank's transaction
data could be released at all.

**That inverts the usual story about synthetic data.** The generator supports a
compliant end-to-end pipeline because its features are `velocity_24h` and
`cross_border`. The real data supports better metrics and cannot support a
compliant decline notice. A production system needs both at once — which is
precisely why it needs its own data and cannot be built on a public dataset
however good the modelling is.

### Downloading it needed engineering, which is its own small lesson

The ARFF endpoint is 156 MB and its host **ignores HTTP Range** — it answers 200
with the whole file, so three separate attempts died at 64 MB, 26 MB and 22 MB
and each retry restarted from zero. Worse, a truncated ARFF *parses fine*: it
just contains fewer rows, and a fraud model fitted on the first 40% of a
time-ordered file is a model fitted on the first two days, with nothing about it
looking wrong.

`fetch_real_data.py` uses the parquet mirror instead (73 MB, and it answers **206
with a Content-Range**), resumes on drop, and verifies by *opening* the file —
parquet keeps its footer at the end, so a truncated file refuses to open rather
than reading short. A strictly better failure.

## What is NOT built

1. **Independent validation.** Developer and validator are the same party. Under
   SR 11-7 this alone blocks production use, and no amount of further writing
   fixes it. Both versions in the change log are recorded as **unsigned**, and
   the retraining pipeline refuses to promote without a signature it cannot
   produce.
2. **IEEE-CIS specifically.** That one does need a Kaggle account. The ULB
   dataset above is real, free and unauthenticated, and it covers the same
   ground for everything except reason codes — where its PCA anonymisation makes
   the compliance step impossible, which is itself the finding. What IEEE-CIS
   would add is *named* features on real data, i.e. the one combination neither
   source here provides.
3. ~~**A container that has been RUN under load.**~~ **DONE, and running it
   found the image could not start at all** — `run_container_load.py`,
   `docs/CONTAINER_LOAD.md`. The build was green and the service raised
   `OSError: libgomp.so.1: cannot open shared object file` on import: lightgbm
   links against the GNU OpenMP runtime, `python:3.12-slim` does not ship it,
   and the pip install of a manylinux wheel resolves perfectly because the
   library it needs at *load* time is a system package pip knows nothing about.
   **That is the whole argument for running a container rather than building
   one**, and it stayed invisible for as long as nobody ran it. Fixed with
   `libgomp1` ahead of the pip layer. Running it also surfaced that the model
   artifact is pickled under scikit-learn 1.8.0 while the image resolves 1.9.0
   — a warning, not a failure, which is what makes it worth recording.
   The service then served **1,200 requests at 8 concurrent with 0 errors**,
   p50 44.84ms / p99 95.16ms, 171 rps.

   Two things this deliberately does **not** claim. It is **not a
   container-versus-host comparison** — the load is driven from inside WSL
   because the container publishes on WSL's loopback, so a host baseline would
   differ in the *client* as well as the server, and the README's claim that
   the two p99s differ remains untested. And the numbers were taken with the
   host at load average ~10, so they are a **floor**, not this service's best
   latency.

4. **Evidently.** *(Still blocked, and re-verified 2026-08-24.)* It now *installs* (`pip install evidently` succeeds) but does
   not import on CPython 3.14: `pydantic.v1.errors.ConfigError: unable to infer
   type for attribute "relative"`, raised from its own pydantic-v1 compatibility
   shim. `monitor.py` covers the same ground and adds the label-free alert-rate
   signal. Recorded as *attempted and blocked*, with the error, rather than as a
   choice.
5. ~~**A real protected attribute.**~~ **DONE** —
   `run_intersectional_real.py` runs this repo's own intersectional machinery
   on 15,587 real HMDA applications carrying race AND sex, both self-reported,
   on the same applicants. That configuration is what intersectional analysis
   needs and is genuinely hard to find. The machinery under test is ML-1's; the
   DECISION is HMDA's — a mortgage approval, not a fraud score — and this
   validates the analysis without turning ML-1 into a lending model.

   The verdict is honestly null: no cell falls below 0.80. **But the direction
   is the more precise reading** — the minority×female cell sits at **0.8443**,
   below both marginals (0.8569 and 0.9878), so the effect the module exists to
   find IS present and simply does not cross the threshold. Reporting that as
   "no finding" would discard it.

   Running it also exposed a limitation of the tool: `intersectional_table`
   iterates over `(0, 1)`, so **both axes must be binary**, forcing race to
   minority/non-minority. That is the exact aggregation ML-3 showed hides a
   failing group on this same data — the aggregate passes at 0.8478 while four
   named groups fail. A binary table can therefore report "no cell below 0.80"
   on a population where a named group is being declined at a failing rate.
6. **Business-necessity documentation.** The AIR, the threshold sweep, the
   ablation and the alternative search all exist; whether `mcc_risk` is justified
   by loss experience is the lender's evidence to produce, not the modeller's to
   assert.
7. **A scheduler** — *the scheduling LOGIC is now built; the invocation is not.*
   `src/schedule.py` decides what is due (cadence follows signal latency:
   alert-rate hourly, score PSI 6-hourly, performance weekly), applies
   hysteresis so a flapping signal does not page repeatedly, coalesces missed
   runs rather than back-filling them — the OPPOSITE of SE-2's settlement
   catch-up, because monitoring is not cumulative — and enforces a retrain
   cooldown an alert cannot override.

   `run_schedule.py` over 14 simulated days: **60 pages under a naive
   every-breach policy, 1 under this one.** Detection delay on the event that
   mattered was 26 hours, of which 24 was the monitoring OUTAGE and 2 the
   deliberate hysteresis — the outage dominated, which is the opposite of where
   tuning attention usually goes.

   ~~Something still has to invoke it~~ — **`ops/install_timers.sh` installs it
   as a real systemd timer, verified firing** (`Result=success`, the pass ran
   and correctly reported `ran=0 skipped=4` because nothing was due). The timer
   is `Persistent=true`, which is safe ONLY because `due()` coalesces, and
   carries a `RandomizedDelaySec` so every host does not fire at `:00`.

   Three real failures were found by installing it rather than describing it:
   the unit pointed at an interpreter without numpy exited 1 with *"MONITORING
   PASS FAILED ... This is not drift"* — the exit-code separation working on a
   real misconfiguration; a Windows interpreter handed a `/mnt/c/` path
   resolved it as `C:\mnt\c\`; and systemd treats backslash in `ExecStart` as
   an escape, so a Windows path came out with a carriage return in it. The
   installer now detects the interpreter, converts the path, and **refuses to
   install a timer that would fail on every fire.**

   The scheduler still stays OUTSIDE the application, which was the original
   argument and still holds. See `docs/SCHEDULE.md`.
